# Machine Log Monitoring System

A simple Python-based machine log monitoring system that reads machine logs, extracts machine information and timestamps, stores the results in PostgreSQL, generates a CSV report, and runs automatically on a schedule.

## Requirements

The application performs five main responsibilities:

1. Reads machine logs.
2. Extracts machine IDs, timestamps, and error messages.
3. Stores the results in PostgreSQL.
4. Generates a report.
5. Runs automatically on a schedule.

Python logging is used for application/runtime logs.

# Machine Log Format

The machine log contains a normal human-readable timestamp.

Example:

```text
2026-10-08 10:16:55 Machine M102 ERROR Motor overheating
2026-10-08 10:18:40 Machine M101 ERROR Sensor failure
2026-10-08 10:20:00 Machine M102 INFO Temperature normal
2026-10-08 10:21:40 Machine M103 ERROR Pressure too high
2026-10-08 10:30:40 Machine M123 INFO Pressure normal
```

The application extracts:

```text
Timestamp      → 2026-10-08 10:16:55
Machine ID     → M102
Log Level      → ERROR
Error Message  → Motor overheating
```

The extracted timestamp is then converted to a Unix timestamp.

```text
Normal timestamp
2026-10-08 10:16:55
        │
        ▼
Unix timestamp
1791442615
```

The application stores **both** values.

> The example conversion assumes the machine log timestamp is in UTC. If the machine produces timestamps in another timezone, the parser should use that timezone when converting to Unix time.

# Timestamp Handling

The machine log contains the normal timestamp.

For example:

```text
2026-10-08 10:16:55
```

The application performs the following:

```text
Machine Log
     │
     ▼
Extract normal timestamp
     │
     ▼
Convert to datetime
     │
     ├──────────────► Store normal timestamp
     │
     ▼
Convert to Unix timestamp
     │
     └──────────────► Store Unix timestamp
```

The original timestamp is **not replaced**.

The database stores:

```text
timestamp
unix_timestamp
```

A third timestamp is also stored:

```text
created_at
```

`created_at` represents when the application processed/stored the machine error.

Therefore:

```text
timestamp
    = time when the machine event occurred

unix_timestamp
    = same machine event represented as Unix time

created_at
    = time when our application processed the record
```

# PostgreSQL Schema

The table is:

```sql
CREATE TABLE IF NOT EXISTS machine_errors (
    id BIGSERIAL PRIMARY KEY,
    machine_id VARCHAR(50) NOT NULL,
    timestamp TIMESTAMPTZ NOT NULL,
    unix_timestamp BIGINT NOT NULL,
    error_message TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,

    CONSTRAINT unique_machine_error
    UNIQUE (machine_id, timestamp, error_message)
);
```

There are no PostgreSQL timestamp defaults.

The application explicitly supplies:

```text
timestamp
unix_timestamp
created_at
```

---

# Duplicate Prevention

The database prevents duplicate machine errors using:

```sql
UNIQUE (machine_id, timestamp, error_message)
```

The insert operation uses:

```sql
ON CONFLICT (machine_id, timestamp, error_message)
DO NOTHING;
```

Therefore, if the scheduler reads the same machine log again, an already stored error is not inserted again.

# Regex Parsing

The machine log has a known structure:

```text
2026-10-08 10:16:55 Machine M102 ERROR Motor overheating
```

The parser uses a regular expression with named groups:

```python
r"(?P<timestamp>\d{4}-\d{2}-\d{2}\s+\d{2}:\d{2}:\d{2})\s+"
r"Machine\s+(?P<machine_id>M\d+)\s+"
r"(?P<level>ERROR|INFO)\s+"
r"(?P<message>.+)"
```

Named groups make the extracted values easier to work with:

```python
match.groupdict()
```

Example result:

```python
{
    "timestamp": "2026-10-08 10:16:55",
    "machine_id": "M102",
    "level": "ERROR",
    "message": "Motor overheating"
}
```

`re.fullmatch()` is used because the complete machine-log line is expected to follow the defined structure.

# ERROR Records

The application stores only `ERROR` records.

For example:

```text
2026-10-08 10:16:55 Machine M102 ERROR Motor overheating
```

is stored.

But:

```text
2026-10-08 10:20:00 Machine M102 INFO Temperature normal
```

is ignored.

# Application Logging

The application uses Python's `logging` module rather than `print()` for runtime activity.

Application logs are written to:

```text
logs/application.log
```

and displayed in the terminal.

Example:

```text
2026-10-08 10:00:00 | INFO | scheduler | Scheduler started
2026-10-08 10:00:00 | INFO | jobs | Monitoring started
2026-10-08 10:00:00 | INFO | log_reader | Read 4 lines from machine log
2026-10-08 10:00:00 | INFO | parser | ERROR detected: machine=M102
2026-10-08 10:00:00 | INFO | db | Error inserted: machine=M102
2026-10-08 10:00:00 | INFO | report | Report generated
2026-10-08 10:00:00 | INFO | jobs | Monitoring completed
```

There are two different types of log files:

### `machine.log`

Contains the data produced by the machines.

```text
2026-10-08 10:16:55 Machine M102 ERROR Motor overheating
```

### `application.log`

Contains information about what the Python application is doing.

```text
2026-10-08 10:00:00 | INFO | parser | ERROR detected: machine=M102
```

These files have different purposes and should remain separate.

# PostgreSQL Example

After processing the machine log, the database could contain:

| id | machine_id | timestamp              | unix_timestamp | error_message     | created_at             |
| -: | ---------- | ---------------------- | -------------: | ----------------- | ---------------------- |
|  1 | M102       | 2026-10-08 10:16:55+00 |     1791442615 | Motor overheating | 2026-10-08 10:25:01+00 |
|  2 | M101       | 2026-10-08 10:18:40+00 |     1791442720 | Sensor failure    | 2026-10-08 10:25:01+00 |
|  3 | M103       | 2026-10-08 10:21:40+00 |     1791442900 | Pressure too high | 2026-10-08 10:25:01+00 |

The important point is that:

```text
timestamp       = original machine event time
unix_timestamp  = Unix representation of that event time
created_at      = application processing time
```

# Scheduling

The monitoring job is executed automatically using APScheduler.

The current configuration runs the monitoring job every minute:

```text
Every 1 minute
      │
      ▼
Read machine log
      │
      ▼
Parse ERROR records
      │
      ▼
Store in PostgreSQL
      │
      ▼
Generate report
```
