# Live IIoT Monitoring Web Application — Step-by-Step Architecture

**Built from:** the existing Machine Sensor API, MQTT/Mosquitto broker, Paho client,
cron_jobs/partitioning, log_rotation, RegEx log monitor, and training documentation in
`/f/Intern_Training/`.
**Audience:** first-time builder who already has sensor readings in PostgreSQL and an API
exposing them, and wants the full architecture to add live monitoring.
**Scope:** end-to-end — data source, ingestion, database, API, dashboard, KPIs, alarms,
observability, security, testing, deployment, retention. Every layer includes what exists
today and what to add.

---

## How to read this architecture

The architecture is a pipeline with six stages. Build them in this order — each stage
feeds the next, and building out of order (charts before data, dashboard before ingestion)
is the most common first-time mistake.

```
Data Source → Ingestion → Database → API → Dashboard → Operations
                (MQTT/TLS)   (tables +      (new endpoints)   (screens +
                simulator)    indexes)                      alarms/KPIs)
```

Each stage below says:

1. What this stage does
2. What this project already has (from the existing code)
3. What to add to make it a live monitoring app
4. The requirements that stage must satisfy

---

## Stage 0 — What we are monitoring (define the operational question)

**What this stage does:** Define the single operational question the dashboard answers.
Everything downstream — KPIs, screens, API endpoints, alarm thresholds — follows from this.

**What this project already has:** A Flask + PostgreSQL API storing machine sensor
readings. Machines have sensor readings ("Machine A has TEMP 72.1 at 10:00"). The existing
API exposes machines, readings, statistics, and an import pipeline.

**What to add:** Decide the question. For this project it is:

> "Which machines are alive, which are stale, which are in warning or critical state, and
> what are their current readings?"

**Requirements this stage produces:**

- A defined set of machine states: healthy, warning, critical, offline, stale
- A definition of "stale" (e.g. no new reading for N seconds — 60 is a reasonable default)
- A definition of "healthy" (recent reading, in range, no active alarm)
- The list of sensor tags and their units (so the dashboard knows what it is showing)

## Stage 1 — Data source (what feeds the system)

**What this stage does:** Produce timestamped sensor readings, either from real machines or
a simulator for development.

**What this project already has:**

- **Existing data:** the pickle snapshot (`all_topics_20250328-114500.pkl`) converted to CSV
  and imported into `sensor_readings` — ~55,918 readings across 12 machines, already in the
  database.
- **MQTT infrastructure:** Mosquitto broker running on Windows as a service on port 8883 with
  TLS/mTLS (CA, server cert, client cert). Config: `require_certificate true`,
  `use_identity_as_username true`, `allow_anonymous false`. Certificates built with OpenSSL;
  see `MQTT/mqtt_readme.md` for the full chain.
- **Paho client demo:** `MQTT/Python/mqttdemo.py` — Callback API v2, TLS on 8883, all five
  callbacks (on_connect, on_subscribe, on_publish, on_message, on_disconnect), return-code
  checks, `logging.exception` in every error path.

**What to add:**

- **A telemetry simulator** for development. Replays the existing CSV as "now" or generates
  periodic readings per machine. This lets you build and test the dashboard before any real
  MQTT client is attached. The simulator writes through the same `reading_service.add_reading()`
  path so you are testing the real pipeline.
- **A decision on the live payload shape.** The IIoT platform plan proposes:

  ```json
  {
    "schema_version": "1.0",
    "message_id": "uuid",
    "machine_id": "M102",
    "sensor_tag": "TEMP",
    "value": 76.4,
    "unit": "degC",
    "measured_at": "2026-10-13T03:35:00Z"
  }
  ```

  Topic convention: `factory/{site_id}/{machine_id}/telemetry`.

**Requirements this stage must satisfy:**

- Readings carry a timestamp in UTC (ISO 8601 with Z, or Unix time). The existing API already
  normalizes to UTC via `utc_z()` in `reading_service.py`.
- Each reading has a machine_id, sensor_tag, numeric sensor_value.
- For live MQTT: the payload must be validated before persistence (schema_version, machine_id
  matches topic, sensor_tag is known, value is numeric/finite, measured_at is valid ISO 8601).
- The source of truth for "latest reading" must be defined — is it the last row in
  `sensor_readings` per machine/sensor, or a separate `machine_status` table updated by the
  ingestion worker? The dashboard should not query "all readings DESC LIMIT 1" per machine on
  every refresh.

## Stage 2 — Ingestion (getting data into the database safely)

**What this stage does:** Take incoming messages (MQTT or simulator), validate, normalize,
deduplicate, and persist them. This is the gate between "data arrived" and "data trusted."

**What this project already has:**

- **Pickle importer** (`services/pickle_importer.py`): two-stage pipeline `.pkl → CSV →
  PostgreSQL`. Validates rows, skips broken ones, batches inserts of 5000 rows via
  `execute_values`, uses a SHA-256 import ledger (`import_batches` table) to prevent
  re-importing the same file. This is the template for how ingestion should behave.
- **Reading service** (`services/reading_service.py`): `add_reading()` inserts a single
  reading with parameterized SQL, handles ForeignKeyViolation → 400, no duplicate check on
  purpose.
- **MQTT client patterns:** the Paho demo shows the five callbacks, return-code checks, and
  the lesson that `subscribe()`/`publish()` return values report the request, while callbacks
  report what the broker did. Both checks matter.

**What to add:**

- **An MQTT ingestion worker** (a separate Python process, not part of the Flask API):
  - Subscribes to `factory/+/+/telemetry` (or a specific topic pattern)
  - On `on_message`: decode payload (UTF-8 with fallback to `repr`), validate against the
    contract, normalize timestamp to UTC, look up or create the machine, insert via
    `reading_service.add_reading()` or a batch insert
  - **Idempotency:** use `message_id` from the payload to detect duplicates. If the same
    message_id was already processed, skip it and log. Do not rely on MQTT QoS alone for dedup
    — assume at-least-once delivery means duplicates are possible.
  - **Never claim database durability just because the MQTT callback fired.** The ingestion
    worker must confirm its own write returned success.
  - **Invalid messages:** count and log with safe diagnostic context (mask any sensitive data,
    never log full payloads that might contain secrets). Do not crash the consumer on one bad
    message — `logging.exception` in the except block, continue to the next.
  - **Retry/replay policy:** if the database is down, use bounded retries with backoff and
    jitter. Do not use an unbounded in-memory queue — the IIoT Python guide identifies the queue
    pattern (MQTT → consumer → queue → worker → PostgreSQL) but for MVP at modest volume, direct
    persistence with bounded retries is acceptable. Document the data-loss behavior for process
    crashes.

**Requirements this stage must satisfy:**

- Validation at the boundary, once, centrally. The IIoT Python guide and the existing
  `utils/validation.py` both say: validate once, centrally, at the boundary, then trust
  downstream.
- UTC everywhere internally. The existing code uses `TIMESTAMPTZ` and `utc_z()` — follow that.
  Convert to local time only at the edge (dashboard display).
- Parameterized SQL only. The existing code already does this — `%s` placeholders for every data
  value, f-strings only for identifiers like schema/table names.
- Transactions: `commit` on success, `rollback` on failure, cleanup in `finally`. The existing
  `database/connection.py` context managers do this — the ingestion worker should use the same
  `db.connection()` / `db.cursor()` pattern.
- Bound everything: connection timeout (5s existing), statement timeout (15s existing), batch size
  (5000 existing), retry count, retry backoff. No unbounded waits, no unbounded queues.

## Stage 3 — Database (what the dashboard queries)

**What this stage does:** Store machines, readings, status, alarms, and (optionally)
message-level traceability. Provide indexes for the dashboard's query patterns.

**What this project already has:**

- `machines` table: `id SERIAL PK, machine_name VARCHAR(100) UNIQUE NOT NULL, created_at TIMESTAMPTZ`
- `sensor_readings` table: `id BIGSERIAL PK, machine_id INTEGER NOT NULL REFERENCES
  machines(id) ON DELETE CASCADE, sensor_tag VARCHAR(50) NOT NULL, sensor_value NUMERIC NOT NULL,
  timestamp TIMESTAMPTZ NOT NULL`
- Indexes: `(machine_id, timestamp)`, `(sensor_tag)`, `(timestamp)`
- `import_batches` ledger: `file_hash CHAR(64) UNIQUE, file_name, records_inserted,
  records_skipped, imported_at`
- Connection pool: `ThreadedConnectionPool` (min 2, max 10), `connect_timeout=5`,
  `statement_timeout=15000`, context managers that always return connections
- Schema namespace: `machine_schema` (from `DB_SCHEMA` config)

**What to add (new tables for a monitoring dashboard):**

**machine_sensors** — the sensor registry. One row per (machine, sensor).

```sql
CREATE TABLE machine_schema.machine_sensors (
    id SERIAL PRIMARY KEY,
    machine_id INTEGER NOT NULL REFERENCES machine_schema.machines(id) ON DELETE CASCADE,
    sensor_tag VARCHAR(50) NOT NULL,
    unit VARCHAR(20) NOT NULL,
    display_name VARCHAR(100),
    warning_threshold NUMERIC,
    critical_threshold NUMERIC,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (machine_id, sensor_tag)
);
```

Why: the dashboard needs to know which sensors belong to which machine, what units to display,
and what thresholds define warning/critical. The unique constraint on `(machine_id, sensor_tag)`
is provable (you configure it), unlike the old `(machine_id, sensor_tag, timestamp)` constraint
that was dropped because it was an unprovable business claim.

**machine_status** — one row per machine, updated by the ingestion worker or a periodic job.
This is the backing table for "is this machine alive / stale / offline?"

```sql
CREATE TABLE machine_schema.machine_status (
    machine_id INTEGER PRIMARY KEY REFERENCES machine_schema.machines(id) ON DELETE CASCADE,
    connection_state VARCHAR(20) NOT NULL DEFAULT 'unknown',
    last_seen_at TIMESTAMPTZ,
    last_reading_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Why: separates connectivity (MQTT client alive) from telemetry freshness (machine producing
healthy readings). A connected MQTT client does not prove the machine is producing healthy
readings.

**alarm_events** — the auditable alarm lifecycle. Every state transition is a row.

```sql
CREATE TABLE machine_schema.alarm_events (
    id BIGSERIAL PRIMARY KEY,
    machine_id INTEGER NOT NULL REFERENCES machine_schema.machines(id) ON DELETE CASCADE,
    sensor_tag VARCHAR(50) NOT NULL,
    severity VARCHAR(20) NOT NULL,
    event_type VARCHAR(20) NOT NULL,
    observed_value NUMERIC,
    threshold_value NUMERIC,
    opened_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    acknowledged_at TIMESTAMPTZ,
    resolved_at TIMESTAMPTZ,
    status VARCHAR(20) NOT NULL DEFAULT 'active'
);
```

Why: alarms are a state machine, not a flag. You need to know when an alarm opened, who
acknowledged it, when it resolved, and what value triggered it. The lifecycle is:
opened → acknowledged → resolved.

**telemetry_messages** (optional) — one row per incoming `message_id` for end-to-end
traceability.

```sql
CREATE TABLE machine_schema.telemetry_messages (
    message_id VARCHAR(64) PRIMARY KEY,
    machine_id INTEGER NOT NULL,
    received_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    processing_status VARCHAR(20) NOT NULL,
    failure_reason TEXT
);
```

Why: debug "did this message make it?" But it needs a retention policy — do not store unlimited
rows without one.

**Indexes to add for dashboard query patterns:**

- `machine_status`: index on `last_seen_at` for "find stale machines"
- `alarm_events`: index on `(status, severity, opened_at)` for "active alarms ordered by severity
  and age"; index on `(machine_id, status)` for "alarms for one machine"
- `sensor_readings`: the existing indexes are sufficient for the API; add an index on
  `(machine_id, sensor_tag, timestamp DESC)` if the dashboard does per-machine-per-sensor
  latest-reading queries and the existing `(machine_id, timestamp)` index is not enough.

**Retention policy (decide in this stage, not later):**

- `alarm_events`: how long do rows stay before archival/deletion? (e.g. 90 days active, then
  archive)
- `telemetry_messages`: if used, define retention (e.g. 7 days for debugging, then drop). Do not
  let this table grow without bound.
- `sensor_readings`: the existing table grows forever unless you add partitioning. For the MVP,
  the existing table is fine. For production volume, consider time-range partitioning by
  `timestamp` (the cron_jobs project in this repo already demonstrates PostgreSQL range
  partitioning with just-in-time partition creation and a composite primary key). The partition
  column must be in the primary key.

**Requirements this stage must satisfy:**

- Enforce only claims that can be proven. The existing project learned this the hard way: an
  unprovable unique constraint multiplied one file ~211× into 11.8M rows. The
  `machine_sensors` unique constraint is provable (you configure it). The `telemetry_messages
  .message_id` unique constraint is provable (the ingestion worker assigns it). Do not add
  uniqueness rules for things the source does not guarantee.
- UTC + `TIMESTAMPTZ` for all timestamps. The existing schema already does this.
- Fail-fast config: `config.py` validates `.env` at boot. The existing pattern — keep it.
- Do not commit real certificates, private keys, passwords, or real `.env` files to source control.
  The existing `.gitignore` should cover this.

## Stage 4 — API (the dashboard's data contract)

**What this stage does:** Expose current status, latest readings, historical ranges, statistics,
and alarms to the dashboard through validated HTTP endpoints. The dashboard is a heavy API client —
every panel polls, so endpoints must be cheap.

**What this project already has:**

- `GET /machines`, `GET /machines/<id>`, `POST /machines`, `PUT`, `DELETE`
- `GET /readings`, `POST /readings`, `GET /readings/<id>`, `PUT`, `DELETE`
- `GET /readings/statistics` — MIN/MAX/AVG with filters (aggregates cast `::float8` so they return
  real JSON numbers, not strings)
- `GET /readings/export` — streaming CSV
- `GET /health` — service + db status (200/503)
- `POST /readings/import` — pickle import
- Shared validators (`utils/validation.py`), shared filter builder (`_build_reading_filters`),
  honest status codes (200/201/400/404/405/409/500/503)
- Eight global error handlers in `app.py` — every failure becomes JSON, no database details leak to
  clients
- `app.py` factory pattern — side-effect-free import, lets waitress/wsgi.py/tests all import cleanly

**What to add (new endpoints for the dashboard):**

**`GET /api/v1/overview`** — the dashboard's home screen data.

```json
{
  "generated_at": "2026-10-13T10:00:00Z",
  "machines": {
    "total": 12,
    "healthy": 8,
    "warning": 2,
    "critical": 1,
    "offline_or_stale": 1
  },
  "active_alarms": 3,
  "latest_reading_age_seconds": {
    "max": 45,
    "avg": 12,
    "stale_count": 1
  }
}
```

Requirements: cheap to compute (use `machine_status` counts and pre-aggregated values, not
`SELECT COUNT(*) FROM sensor_readings`). Include a `generated_at` timestamp so the dashboard knows
how fresh the data is.

**`GET /api/v1/machines/<id>/status`** — one machine's operational status.

```json
{
  "machine_id": 1,
  "machine_name": "Machine A",
  "connection_state": "connected",
  "last_seen_at": "2026-10-13T10:00:00Z",
  "last_reading_at": "2026-10-13T09:58:00Z",
  "sensors": [
    {"sensor_tag": "TEMP", "value": 76.4, "unit": "degC",
     "warning_threshold": 80, "critical_threshold": 95, "status": "healthy"}
  ]
}
```

Requirements: one query, bounded. Use `machine_status` + `machine_sensors` + latest reading per
sensor (a small query, not a full table scan).

**`GET /api/v1/machines/<id>/readings/latest`** — latest reading per sensor for one machine.
Reuse for the machine detail screen.

**`GET /api/v1/readings`** — reuse existing `/readings` with filters (machine_id, sensor_tag, from,
to) and pagination. Keep the existing endpoint; add `/api/v1/` version.

**`GET /api/v1/readings/statistics`** — reuse existing `/readings/statistics` for min/max/avg over a
bounded period.

**`GET /api/v1/alarms`** — filter by status, severity, machine_id, from, to. Return
active/acknowledged/resolved alarms with the lifecycle fields.

**`POST /api/v1/alarms/<id>/acknowledge`** — operator acknowledges an alarm. Requires authentication
(add auth before this endpoint, not after).

**Requirements this stage must satisfy:**

- Do not expose raw database errors. The existing eight error handlers already do this right — keep
  the discipline for new endpoints.
- Do not return `Decimal` as strings. The existing capstone already fixed this (aggregates cast
  `::float8` in SQL). Make sure any new aggregate endpoints do the same.
- Paginate everything that can be large. The dashboard overview should not scan the entire readings
  table.
- Keep existing routes working. Introduce `/api/v1/` as a versioned namespace so the dashboard can
  depend on stable endpoints while the existing `/machines`, `/readings` stay backward-compatible.
- Add `generated_at` or `updated_at` to responses that represent a snapshot, so the dashboard knows
  how fresh the data is.
- The API remains the access-control and data-contract boundary. The dashboard must not connect
  directly to MQTT or the database.

## Stage 5 — Dashboard (what the operator sees)

**What this stage does:** Present operational status, current readings, trends, and alarms in a
browser. Consumes the API layer. Does NOT connect directly to MQTT, and does NOT hold its own copy
of the database.

**What this project already has:** Nothing dashboard-specific yet. The API is the backend only. The
`mqtt_dashboard_changes/` folder contains a Vue 3 + TypeScript dashboard with SSE, but that is a
separate exploration, not the basis for this architecture.

**What to build — four screens (from the IIoT platform plan, restated as build guidance):**

### Screen A — Operations overview (build this first)

The first thing an operator sees. Answers: "How many machines? How many are okay? Are there alarms?"

Contents:

- KPI strip: total machines, healthy, warning, critical, offline/stale
- Active alarms count, ordered by severity and age
- Machine status table: machine name, last_seen_at, current reading per important sensor, status
  badge (healthy/warning/critical/offline/stale)
- Telemetry freshness indicator (e.g. "data refreshed 2 seconds ago")
- A visible "last updated" timestamp

### Screen B — Machine detail

Answers: "What is this machine doing right now? What is its history?"

Contents:

- Machine identity (name, site/line if configured)
- Connectivity status and telemetry freshness
- Current values for each configured sensor, with units and threshold context (e.g. "TEMP 76.4
  degC — warning threshold 80, critical 95")
- Time-series chart with selectable window (1h / 6h / 24h / 7d)
- Recent alarms for this machine
- Historical readings table (paginated) and export action where authorized

### Screen C — Alarms and events

Answers: "What needs my attention? What happened?"

Contents:

- Alarm list, filterable by status (active/acknowledged/resolved), severity, machine, sensor, time
  range
- Each alarm shows: machine, sensor, observed value, threshold, event time, opened_at,
  acknowledged_at (if any), resolved_at (if any), status
- Acknowledgement action (protected by auth) — operator confirms they saw it
- Resolution history — who acknowledged, when resolved

### Screen D — Historical analysis

Answers: "What was the trend over the last day/week? What were the min/max/avg?"

Contents:

- Machine and sensor selectors
- Time-range picker with server-side pagination
- Trend chart (readings over time)
- Min/max/average summary for the selected range (reuses `/readings/statistics`)
- CSV export for the filtered range (reuses `/readings/export` or a dashboard-specific endpoint)

**Visual direction:**

- Industrial operations-console layout: compact status cards, dense but readable machine table,
  prominent alarm severity
- Restrained colors — use color deliberately for severity, not decoration
- Dark or light theme based on operator environment (control rooms often prefer dark)
- Charts with clearly labeled units and time axes
- Avoid decorative charts that do not answer an operational question

**Live update strategy:**

- Release 1: poll the API at 2–5 second intervals. This is simple, works, and is fine for an MVP
  with a few dashboard users.
- Release 2: add Server-Sent Events (SSE) or WebSockets only if polling latency or request load
  becomes a measured problem. Do not add this on day one — measure first.
- Never connect the browser directly to MQTT. Never expose broker credentials to the frontend. The
  backend is the boundary.

**Requirements this stage must satisfy:**

- The dashboard must handle empty states (no machines, no readings), stale states, and API error
  states visibly. Do not show a blank screen or an infinite loader when there is no data — show "no
  machines configured" or "no readings in this range."
- Stale data must be visibly different from healthy data. A machine with no reading for 30 minutes
  is not "healthy" — it is "stale."
- Every chart must answer an operational question. If a chart does not help the operator decide
  something, it is decoration.
- The dashboard must work with real data from day one. Build Screen A with real database-backed data
  first; that proves the pipeline. Then add charts.

## Stage 6 — KPIs (what to measure and show)

### Operator-facing KPIs (shown on the dashboard)

These are the numbers an operator cares about. Every one should be computable from the database and
cheap to query.

| KPI | What it means | How to compute |
|---|---|---|
| Total machines | Fleet size | `SELECT COUNT(*) FROM machines` |
| Healthy machines | Machines with recent, in-range readings and no active alarms | Join `machine_status` with alarm state; define "healthy" explicitly |
| Warning machines | Machines with a sensor in warning range or a warning alarm | `warning_threshold` breached, or active warning alarm |
| Critical machines | Machines with a sensor in critical range or a critical alarm | `critical_threshold` breached, or active critical alarm |
| Offline / stale machines | Machines with no recent reading or no recent MQTT connectivity | `last_seen_at` older than threshold, or `connection_state` disconnected |
| Active alarms | Alarms currently open (not resolved) | `SELECT COUNT(*) FROM alarm_events WHERE status = 'active'` |
| Latest reading age | How old is the newest reading per machine | `MAX(EXTRACT(EPOCH FROM (NOW() - last_reading_at)))` per machine, or pre-computed in `machine_status` |
| Telemetry freshness | When did the dashboard data last refresh | Dashboard-side timestamp, sent with every API response |

### System-facing KPIs (shown in logs/metrics, not necessarily on the dashboard)

These are for you, the builder, to know the system is healthy.

| KPI | Why it matters |
|---|---|
| MQTT messages received | Is the ingestion worker receiving anything? |
| Messages accepted | How many passed validation? |
| Messages rejected | How many failed validation? (should be low, but visible) |
| Duplicate messages detected | Is the dedup working? (idempotency check) |
| Messages persisted | How many actually made it to PostgreSQL? |
| Ingestion latency | Time from message received to database commit |
| Database write latency | How long do inserts take? |
| Database pool usage | Is the pool saturated? (pool min/max from config: 2/10) |
| Database timeouts | How often does statement_timeout fire? (should be rare) |
| API latency | P95/P99 response time for dashboard endpoints |
| API error rate | 4xx/5xx ratio for dashboard endpoints |
| Stale machine count | How many machines have not been seen recently? |

**Requirements this stage must satisfy:**

- Start with the operator KPIs on the dashboard, and log the system KPIs. Do not try to build a full
  Prometheus dashboard on day one.
- The first question is "is the data flowing?" — messages received → accepted → persisted. If those
  three numbers line up, the pipeline works. If they don't, the dashboard is showing fiction.
- Log system KPIs with structured logs (the existing `utils/logger.py` uses rotating file handler at
  10 MB × 5, UTC timestamps, `logger.propagate = False`). Add correlation IDs when you can, but start
  with message_id from the MQTT payload as the correlation key.

## Stage 7 — Alarms (when something is wrong)

**What this stage does:** Detect threshold breaches and record the alarm lifecycle: opened →
acknowledged → resolved.

**What this project already has:** Nothing alarm-specific yet. The capstone stores readings, not
events. The statistics endpoint (min/max/avg) is historical, not real-time.

**What to add:**

- **Threshold configuration** in `machine_sensors`: `warning_threshold`, `critical_threshold` per
  sensor. This makes alarms configurable per machine/sensor instead of hard-coded.
- **Alarm evaluation** in the ingestion worker (or a separate evaluation step):
  - When a reading arrives, compare `sensor_value` against the thresholds for that machine/sensor.
  - If `value >= critical_threshold` → create/continue a critical alarm.
  - If `value >= warning_threshold` → create/continue a warning alarm.
  - If `value < warning_threshold` and an alarm was open → resolve it.
- **Alarm lifecycle table** (`alarm_events`): every transition is a row. This makes alarms auditable —
  you can reconstruct the full history of an alarm.
- **Alarm state decision** — answer this explicitly: when a machine keeps breaching the same
  threshold, do you create a new alarm event for every reading, or update the existing active alarm?
  For the MVP, the common choice is: one active alarm per (machine, sensor, severity) at a time; new
  breaches update the existing alarm's `observed_value` and `last_seen_at`; resolution closes it. This
  avoids alarm spam.

**Requirements this stage must satisfy:**

- Alarms are a state machine. Write down the transitions before building the table:
  - What opens an alarm? (threshold breach)
  - What acknowledges it? (operator action)
  - What resolves it? (value back below threshold, or operator action)
  - Can the same machine/sensor have two active alarms of the same severity? (usually no)
  - What happens if the ingestion worker restarts mid-alarm? (alarm state is in the database, so it
    survives; that is why the lifecycle is persisted, not held in memory)
- Survive restarts by storing state in the database, not in the worker's memory.
- Do not alert spam. One active alarm per (machine, sensor, severity) at a time is the common rule.
  Repeated breaches update the existing alarm, not create new ones.
- Acknowledgement is an operator action protected by auth. Do not auto-acknowledge.

## Stage 8 — Observability, security, and operations

### Observability

- **Logging:** the existing `utils/logger.py` uses a rotating file handler (10 MB × 5 archives),
  UTC timestamps, `logger.propagate = False`, and a console handler. Extend this to log ingestion
  metrics (messages received/accepted/rejected/duplicated/persisted), ingestion latency, database write
  latency, and alarm transitions.
- **Health checks:** the existing `/health` endpoint checks database connectivity (200/503). Add a
  liveness endpoint (`/health/live` — process is up) and a readiness endpoint (`/health/ready` — can
  serve traffic, including database and MQTT broker connectivity).
- **Metrics:** start with structured logs. Add Prometheus-style metrics (message counters, latency
  histograms, pool usage gauges) when you have a metrics collector. Do not build a metrics dashboard
  before the operational dashboard works.

### Security

- **TLS/mTLS for MQTT:** the existing Mosquitto config already enforces this (port 8883,
  `require_certificate true`, `use_identity_as_username true`, `allow_anonymous false`). Keep it. Never
  disable hostname verification to work around certificate errors.
- **Broker ACLs:** restrict which clients can publish to which topics. The ingestion worker subscribes
  to `factory/+/+/telemetry`; machines publish to their own topic. Do not let any client publish to any
  topic.
- **Secrets:** the existing `config.py` reads from `.env` and fails fast if required variables are
  missing. Keep this. Store secrets in environment configuration, not source control. Rotate credentials
  exposed in archives.
- **Dashboard/API auth:** the existing API is open on purpose for local learning. For any production
  deployment or dashboard write operations (alarm acknowledge), add authentication. Start with the minimum
  that covers the access model (API key / token for the dashboard is enough for an MVP; full JWT/OAuth is
  a later step).
- **Input validation:** the existing `utils/validation.py` validates at the boundary. Keep this for the
  API. For MQTT ingestion, validate the payload at the boundary too.
- **CORS, payload sizes, request rates:** restrict these on the API when the dashboard is exposed beyond
  localhost.

### Operations

- **Retention policy:** decide when you add the table (Stage 3), not later. Even a simple policy is better
  than none.
- **Backup and restore:** PostgreSQL backup strategy before the dashboard goes live.
- **Restart and recovery:** document how to restart the ingestion worker, the API, and the broker, and what
  state survives each restart (alarm state in DB survives; in-memory state does not).
- **Deployment:** the existing `app.py` uses waitress on port 8080. The ingestion worker is a separate
  process. Document how to run both, how to monitor both, and how to restart each without affecting the other.

## Stage 10 — Build sequence (what to do first, second, third)

### Step 1 — Make the data real (Stage 1 + 3)

- Confirm the existing readings are in the database (the import already loaded ~55,918 readings across 12
  machines).
- Add `machine_sensors` and `machine_status` tables. Backfill `last_seen_at` from existing readings so the
  overview has something to show.
- Add the alarm tables (`alarm_events`) with the lifecycle columns.
- Decide the retention policy for any new table that accumulates data.

### Step 2 — Add the dashboard API endpoints (Stage 4)

- Add `/api/v1/overview` — total/healthy/warning/critical/offline counts, active alarms, latest reading age.
- Add `/api/v1/machines/<id>/status` — connectivity, freshness, latest values per sensor.
- Reuse `/readings` and `/readings/statistics` for historical queries.
- Add `/api/v1/alarms` and `POST .../acknowledge` when you are ready for Screen C.
- Add auth for write operations before or at the same time as the alarm acknowledge endpoint.

### Step 3 — Build Screen A (Stage 5)

- KPI strip + machine status table + active alarms + last-updated timestamp.
- Poll the API every 2–5 seconds.
- Make sure stale/offline is visible and distinct from healthy.
- This is the minimum viable dashboard — it proves the pipeline from database → API → browser.

### Step 4 — Build Screen B (Stage 5)

- Machine detail with current values, units, thresholds.
- One time-series chart with a selectable window (start with 1h).
- Recent alarms for the machine.

### Step 5 — Build Screen C (Stage 7)

- Alarm list with status/severity/machine/time filters.
- Acknowledge action (auth required).
- Resolution history.

### Step 6 — Build Screen D (Stage 5)

- Historical analysis: machine/sensor selectors, time range, trend chart, min/max/avg, CSV export.

### Step 7 — Add the refinements (Stage 6, 8)

- System KPIs in logs/metrics (messages received/accepted/persisted, latencies).
- Retention policy for new tables.
- Auth for dashboard write operations.
- SSE/WebSockets only if polling is proven to be the bottleneck.
- Dashboard testing: loading, empty, stale, error, and populated states.
- Production hardening: auth, reconnect handling, deployment configuration, backup/restore.
