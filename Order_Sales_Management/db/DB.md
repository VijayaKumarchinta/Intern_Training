# As for the Database

## Schema
- `order_sales`
  - Groups all tables related to users, customers, products, orders, and order items.

## Tables

### 1. Users

Stores application user accounts, authentication details, account verification information, and timestamps.

- `id`
  - Uses `INTEGER` as the data type.
  - PostgreSQL generates the value automatically using `GENERATED ALWAYS AS IDENTITY`.
  - Set as the **Primary Key (PK)** to uniquely identify every user.

- `email`
  - Uses `VARCHAR(255)` to store the user's email address.
  - Cannot be `NULL`.
  - A unique index on `LOWER(email)` prevents duplicate email addresses regardless of letter case.
  - The original email value is preserved as entered; uniqueness is case-insensitive.

- `password_hash`
  - Uses `VARCHAR(255)` to store the securely generated password hash.
  - Cannot be `NULL`.
  - Must store a password hash generated by a secure password-hashing algorithm, never a plaintext password.

- `full_name`
  - Uses `VARCHAR(255)` to store the user's full name.
  - Allows `NULL` when the name is not provided.

- `role`
  - Uses `VARCHAR(20)` to store the user's application role.
  - Cannot be `NULL`.
  - Defaults to `'customer'` when no role is supplied.
  - A `CHECK` constraint permits only `'admin'` or `'customer'`.

- `is_verified`
  - Uses `BOOLEAN` to indicate whether the user's account has been verified.
  - Cannot be `NULL`.
  - Defaults to `FALSE`.

- `verification_token_hash`
  - Uses `VARCHAR(255)` to store the hash of the account-verification token.
  - Allows `NULL` when no verification token is pending.

- `verification_expires_at`
  - Uses `TIMESTAMPTZ` to store the verification token's expiration date and time.
  - Allows `NULL` when no expiration time is applicable.

- `reset_token_hash`
  - Uses `VARCHAR(255)` to store the hash of the password-reset token.
  - Allows `NULL` when no password-reset token is pending.

- `reset_token_expires_at`
  - Uses `TIMESTAMPTZ` to store the password-reset token's expiration date and time.
  - Allows `NULL` when no expiration time is applicable.

- `created_at`
  - Uses `TIMESTAMPTZ` to record when the user record was created.
  - Cannot be `NULL`.
  - Defaults to `NOW()`.

- `updated_at`
  - Uses `TIMESTAMPTZ` to record the last modification time of the user record.
  - Cannot be `NULL`.
  - Defaults to `NOW()` when the record is created.
  - Must be updated by the application or a database trigger whenever the record changes.

### 2. Customers

Stores customer details and optionally links a customer to an application user account.

- `customer_id`
  - Uses `VARCHAR(20)` to store the customer's business identifier, such as `CUST1001`.
  - Set as the **Primary Key (PK)**.
  - Cannot be `NULL` and must be unique.

- `user_id`
  - Uses `INTEGER` to reference the associated application user.
  - Acts as a **Foreign Key (FK)** referencing `users.id`.
  - Has a `UNIQUE` constraint, allowing each user to be associated with at most one customer.
  - Allows `NULL` when the customer does not have an application account.
  - Uses `ON DELETE SET NULL` so that deleting the associated user account does not delete the customer record.

- `cust_name`
  - Uses `VARCHAR(255)` to store the customer's name.
  - Allows `NULL` when the name is unavailable.

- `email`
  - Uses `VARCHAR(255)` to store the customer's contact email address.
  - Allows `NULL` when the email is unavailable.
  - Is not unique in the current design.

- `created_at`
  - Uses `TIMESTAMPTZ` to record when the customer record was created.
  - Cannot be `NULL`.
  - Defaults to `NOW()`.

### 3. Products

Stores the product catalogue and each product's current price.

- `product_id`
  - Uses `INTEGER` as the data type.
  - PostgreSQL generates the value automatically using `GENERATED ALWAYS AS IDENTITY`.
  - Set as the **Primary Key (PK)** to uniquely identify each product.

- `pro_name`
  - Uses `VARCHAR(100)` to store the product name.
  - Cannot be `NULL`.
  - Must be unique so that duplicate product names cannot be inserted.

- `current_price`
  - Uses `NUMERIC(12,2)` to store the product's current price with two decimal places.
  - Allows `NULL` if the price has not been configured.
  - A `CHECK` constraint prevents negative prices.
  - Uses an exact decimal data type suitable for monetary calculations.

### 4. Orders

Stores order-level information, including the customer, order date, and current order status.

- `order_id`
  - Uses `VARCHAR(20)` to store the order's business identifier, such as `ORD1001`.
  - Set as the **Primary Key (PK)**.
  - Cannot be `NULL` and must be unique.

- `customer_id`
  - Uses `VARCHAR(20)` to reference the customer who placed the order.
  - Acts as a **Foreign Key (FK)** referencing `customers.customer_id`.
  - Cannot be `NULL`, ensuring that every order belongs to an existing customer.

- `order_date`
  - Uses `DATE` to store the order's calendar date.
  - Allows `NULL` in the current design.
  - Supports date-wise order filtering and sales reporting.

- `order_status`
  - Uses `VARCHAR(20)` to store the current status of the order.
  - Cannot be `NULL`.
  - Defaults to `'Pending'`.
  - A `CHECK` constraint permits only `'Pending'`, `'Received'`, `'Shipped'`, `'Delivered'`, `'Cancelled'`, or `'Returned'`.
  - The application must enforce valid transitions between statuses.

- `created_at`
  - Uses `TIMESTAMPTZ` to record when the order record was created.
  - Cannot be `NULL`.
  - Defaults to `NOW()`.

- `updated_at`
  - Uses `TIMESTAMPTZ` to record the last modification time of the order record.
  - Cannot be `NULL`.
  - Defaults to `NOW()` when the order is created.
  - Must be updated by the application or a database trigger whenever the order changes.

### 5. Order Items

Stores the individual products included in each order, including their quantities and the prices charged at the time of the order.

- `order_item_id`
  - Uses `INTEGER` as the data type.
  - PostgreSQL generates the value automatically using `GENERATED ALWAYS AS IDENTITY`.
  - Set as the **Primary Key (PK)** to uniquely identify each order-item record.

- `order_id`
  - Uses `VARCHAR(20)` to reference the associated order.
  - Acts as a **Foreign Key (FK)** referencing `orders.order_id`.
  - Cannot be `NULL`.
  - Uses `ON DELETE CASCADE`, so deleting an order also deletes its associated order-item records.

- `product_id`
  - Uses `INTEGER` to reference the associated product.
  - Acts as a **Foreign Key (FK)** referencing `products.product_id`.
  - Cannot be `NULL`.
  - Ensures that every order item references an existing product.

- `quantity`
  - Uses `INTEGER` to store the quantity of a product ordered.
  - Cannot be `NULL`.
  - A `CHECK` constraint requires the quantity to be greater than zero.

- `unit_price`
  - Uses `NUMERIC(12,2)` to store the price charged per unit in that particular order.
  - Cannot be `NULL`.
  - A `CHECK` constraint prevents negative prices.
  - Preserves the historical transaction price even if the product's current catalogue price changes.

- `UNIQUE (order_id, product_id)`
  - A table-level unique constraint that prevents the same product from appearing in multiple rows within the same order.
  - Requires repeated quantities of the same product to be combined into one order-item row.

## Indexes

The database also defines the following indexes to improve common query performance.

- `uq_users_email_lower`
  - A unique expression index on `LOWER(email)`.
  - Prevents email duplicates regardless of letter case.

- `idx_orders_customer_date`
  - An index on `(customer_id, order_date)`.
  - Supports customer order-history queries and customer-specific date-range filtering.

- `idx_orders_status`
  - An index on `order_status`.
  - Supports filtering and tracking orders by status.

- `idx_order_items_product`
  - An index on `product_id`.
  - Supports product-wise order lookups and sales aggregation.

Primary keys and unique constraints also create their own indexes automatically.

## Additional Table: Staging Orders

### 6. Staging Orders

Temporarily stores raw records imported from the CSV dataset before validation and insertion into the normalized business tables.

- `order_id`
  - Uses `TEXT` to preserve the raw order identifier from the CSV.

- `order_date`
  - Uses `TEXT` to preserve the raw date representation before date validation and conversion.

- `customer_id`
  - Uses `TEXT` to preserve the raw customer identifier.

- `product`
  - Uses `TEXT` to preserve the raw product name before matching it with the product catalogue.

- `quantity`
  - Uses `TEXT` to preserve the raw quantity before validating and converting it to an integer.

- `unit_price`
  - Uses `TEXT` to preserve the raw price before validating and converting it to `NUMERIC(12,2)`.

- `order_status`
  - Uses `TEXT` to preserve the raw order status before checking whether it is an allowed value.

The staging table intentionally has no primary key, foreign keys, or strict business validation constraints in the current design. This allows raw input to be loaded before it is validated.

The application or import process must validate the staging records and insert valid data into `customers`, `products`, `orders`, and `order_items`.

## Database Design Principles

- **Primary keys:** Uniquely identify records.
- **Foreign keys:** Maintain valid relationships between tables.
- **Unique constraints:** Prevent duplicate values or combinations where required.
- **Check constraints:** Enforce permitted roles, statuses, quantities, and prices.
- **Appropriate data types:** Use integer identifiers, strings for business IDs, `DATE` for calendar dates, `TIMESTAMPTZ` for timestamps, and `NUMERIC` for monetary values.
- **Normalization:** Keep user accounts, customers, products, orders, and order items in separate tables to reduce duplication.
- **Historical accuracy:** Store the transaction-specific unit price in `order_items`.
- **Staging and validation:** Separate raw CSV input from validated business records.
- **Indexes:** Support frequent customer, status, and product queries.

The Flask application connects to this pre-created schema and implements the application logic for customer order management, input validation, order-total calculation, duplicate detection, status updates, and product-wise and date-wise sales reports.

## How to load the dataset

The dataset is loaded in stages so bad rows can be reviewed before they reach the normalized tables.

Source file:

- `data/Online_Store_Orders.csv`

Expected columns:

- `OrderID`
- `Date`
- `CustomerID`
- `Product`
- `Quantity`
- `UnitPrice`
- `OrderStatus`

### Step 1: Create the schema and tables

Run the schema script first.

```bash
psql -U postgres -d order_sales_db -f F:\Intern_Training\Order_Sales_Management\db\init.sql
```

Or from inside psql:

```sql
\i db/init.sql
```

This creates the `order_sales` schema and all tables, including `staging_orders`.

### Step 2: Load the CSV into staging

If PostgreSQL can read the file directly:

```sql
COPY order_sales.staging_orders (
    order_id,
    order_date,
    customer_id,
    product,
    quantity,
    unit_price,
    order_status
)
FROM 'F:/Intern_Training/Order_Sales_Management/data/Online_Store_Orders.csv'
WITH (FORMAT CSV, HEADER TRUE);
```

Use the actual absolute path to the CSV. If the file is only on your local machine and the server cannot reach it, import with pgAdmin or another client tool into `order_sales.staging_orders`.

Quick row check:

```sql
SELECT COUNT(*) AS staging_rows
FROM order_sales.staging_orders;
```

### Step 3: Validate staging rows

Check for missing values first:

```sql
SELECT *
FROM order_sales.staging_orders
WHERE NULLIF(TRIM(order_id), '') IS NULL
   OR NULLIF(TRIM(customer_id), '') IS NULL
   OR NULLIF(TRIM(product), '') IS NULL
   OR NULLIF(TRIM(quantity), '') IS NULL
   OR NULLIF(TRIM(unit_price), '') IS NULL
   OR NULLIF(TRIM(order_status), '') IS NULL;
```

Check date format:

```sql
SELECT *
FROM order_sales.staging_orders
WHERE NULLIF(TRIM(order_date), '') IS NULL
   OR TRIM(order_date) !~ '^\d{4}-\d{2}-\d{2}$';
```

Check quantities:

```sql
SELECT *
FROM order_sales.staging_orders
WHERE CASE
    WHEN TRIM(quantity) ~ '^[0-9]+$'
    THEN TRIM(quantity)::NUMERIC <= 0
    ELSE TRUE
END;
```

Check prices:

```sql
SELECT *
FROM order_sales.staging_orders
WHERE CASE
    WHEN TRIM(unit_price) ~ '^[0-9]+(\.[0-9]{1,2})?$'
    THEN TRIM(unit_price)::NUMERIC < 0
    ELSE TRUE
END;
```

Check statuses:

```sql
SELECT TRIM(order_status) AS status, COUNT(*) AS row_count
FROM order_sales.staging_orders
GROUP BY TRIM(order_status)
ORDER BY status;
```

Allowed statuses:

- Pending
- Received
- Shipped
- Delivered
- Cancelled
- Returned

### Step 4: Insert customers and products

Insert distinct customers:

```sql
INSERT INTO order_sales.customers (customer_id)
SELECT DISTINCT TRIM(customer_id)
FROM order_sales.staging_orders
WHERE NULLIF(TRIM(customer_id), '') IS NOT NULL
ON CONFLICT (customer_id) DO NOTHING;
```

Insert distinct products:

```sql
INSERT INTO order_sales.products (pro_name)
SELECT DISTINCT TRIM(product)
FROM order_sales.staging_orders
WHERE NULLIF(TRIM(product), '') IS NOT NULL
ON CONFLICT (pro_name) DO NOTHING;
```

Customer names and emails are not in this dataset, so `cust_name` and `email` stay NULL unless filled later. Do not set `current_price` from old order prices unless there is a defined rule for choosing the current price.

### Step 5: Insert orders and order items

Insert order headers:

```sql
INSERT INTO order_sales.orders (
    order_id,
    customer_id,
    order_date,
    order_status
)
SELECT DISTINCT
    TRIM(s.order_id),
    TRIM(s.customer_id),
    TRIM(s.order_date)::DATE,
    INITCAP(LOWER(TRIM(s.order_status)))
FROM order_sales.staging_orders AS s
WHERE NULLIF(TRIM(s.order_id), '') IS NOT NULL
  AND NULLIF(TRIM(s.customer_id), '') IS NOT NULL
  AND NULLIF(TRIM(s.order_date), '') IS NOT NULL
  AND TRIM(s.order_date) ~ '^\d{4}-\d{2}-\d{2}$'
  AND LOWER(TRIM(s.order_status)) IN (
      'pending', 'received', 'shipped',
      'delivered', 'cancelled', 'returned'
  )
ON CONFLICT (order_id) DO NOTHING;
```

Insert order items:

```sql
INSERT INTO order_sales.order_items (
    order_id,
    product_id,
    quantity,
    unit_price
)
SELECT
    TRIM(s.order_id),
    p.product_id,
    TRIM(s.quantity)::INTEGER,
    TRIM(s.unit_price)::NUMERIC(12,2)
FROM order_sales.staging_orders AS s
JOIN order_sales.orders AS o
  ON o.order_id = TRIM(s.order_id)
JOIN order_sales.products AS p
  ON p.pro_name = TRIM(s.product)
WHERE TRIM(s.quantity) ~ '^[0-9]+$'
  AND TRIM(s.quantity)::NUMERIC > 0
  AND TRIM(s.unit_price) ~ '^[0-9]+(\.[0-9]{1,2})?$'
  AND TRIM(s.unit_price)::NUMERIC >= 0
ON CONFLICT (order_id, product_id) DO NOTHING;
```

### Step 6: Verify the load

Check counts:

```sql
SELECT COUNT(*) AS customers FROM order_sales.customers;
SELECT COUNT(*) AS products  FROM order_sales.products;
SELECT COUNT(*) AS orders      FROM order_sales.orders;
SELECT COUNT(*) AS order_items FROM order_sales.order_items;
```

Confirm there is still one header per order:

```sql
SELECT
    order_id,
    COUNT(*) AS header_count
FROM order_sales.orders
GROUP BY order_id
HAVING COUNT(*) > 1;
```

Sample order with line items:

```sql
SELECT
    o.order_id,
    o.order_date,
    o.order_status,
    c.cust_name,
    oi.product_id,
    p.pro_name,
    oi.quantity,
    oi.unit_price,
    oi.quantity * oi.unit_price AS line_total
FROM order_sales.orders AS o
JOIN order_sales.customers AS c
  ON c.customer_id = o.customer_id
JOIN order_sales.order_items AS oi
  ON oi.order_id = o.order_id
JOIN order_sales.products AS p
  ON p.product_id = oi.product_id
WHERE o.order_id = 'PUT_ONE_ORDER_ID_HERE'
ORDER BY oi.order_item_id;
```

Order total:

```sql
SELECT
    o.order_id,
    COALESCE(SUM(oi.quantity * oi.unit_price), 0)::NUMERIC(14,2) AS order_total
FROM order_sales.orders AS o
LEFT JOIN order_sales.order_items AS oi
  ON oi.order_id = o.order_id
WHERE o.order_id = 'PUT_ONE_ORDER_ID_HERE'
GROUP BY o.order_id;
```

### Step 7: Reconcile rejected rows

Do not assume the load is complete just because there were no SQL errors. Compare staging rows with imported rows:

```sql
SELECT
    s.order_id,
    s.product,
    s.quantity,
    s.unit_price,
    s.order_status,
    CASE
        WHEN oi.order_item_id IS NOT NULL THEN 'imported'
        ELSE 'not imported'
    END AS load_result
FROM order_sales.staging_orders AS s
LEFT JOIN order_sales.order_items AS oi
  ON oi.order_id = TRIM(s.order_id)
 AND oi.product_id = (
        SELECT p.product_id
        FROM order_sales.products AS p
        WHERE p.pro_name = TRIM(s.product)
    )
ORDER BY s.order_id, s.product;
```

If any rows are marked `not imported`, record why. Common reasons:

- missing or malformed required fields
- invalid date, quantity, or price
- unrecognized status
- customer or product not found
- duplicate `order_id` and `product_id` already existed

### Recommended dataset load order

1. `psql -d order_sales_db -f db/init.sql`
2. `COPY` the CSV into `order_sales.staging_orders`
3. Run the staging validation queries
4. Insert customers
5. Insert products
6. Insert orders
7. Insert order items
8. Run the count and sample queries
9. Reconcile any rows that were not imported
