# PlantView — Line 30 Live Dashboard

Software documentation for the integrated PlantView Line 30 dashboard.

## 1. Overview

PlantView is a live telemetry dashboard for Line 30. It ingests process
telemetry from an MQTT broker, persists it in PostgreSQL, exposes it through a
Flask REST API, streams it live to the browser with Socket.IO, and lets
operators inspect live values, hourly performance, replay cycles, and CSV
exports.

The project is a monorepo-style integration containing:

- `frontend/`: Vue 3 + Vite web UI.
- `server/`: Flask + Flask-SocketIO backend.
- `db/schema.sql`: PostgreSQL schema.
- `publisher/`: optional replay/publisher tooling.

## 2. System components

| Component | Technology | Role |
| --- | --- | --- |
| MQTT broker | external | source of Line 30 telemetry |
| Backend | Flask + Flask-SocketIO | REST API, ingest, live broadcast |
| Database | PostgreSQL | telemetry, events, alarm state, exports |
| Frontend | Vue 3 + Vite | dashboard UI, charts, history, exports |
| Socket.IO client | socket.io-client | live stream from server to browser |
| Charts | ECharts + vue-echarts | process trends and relationships |
| State | Pinia | shared client state |
| SQL | SQLAlchemy | database access |

## 3. Architecture overview

```text
MQTT broker
  |
  | topic: factory/line30/telemetry (QoS 1)
  v
paho.mqtt subscriber (server/mqtt/subscriber.py)
  |
  | on_message -> validate -> save_telemetry()
  | -> broadcast_telemetry(record, payload)
  | -> broadcast_operational_events(record)
  v
Flask + Flask-SocketIO (server/run.py, server/app.py)
  |-- /api/health
  |-- /api/telemetry/latest
  |-- /api/telemetry/history
  |-- /api/telemetry/statistics
  |-- /api/summary/hourly
  |-- /api/events
  |-- /api/history/cycles
  |-- /api/exports/*.csv
  |
  |-> Socket.IO room: line:line30
        |-> telemetry_update
        |-> operational_event
  v
Vue 3 + Vite frontend
```

## 4. Data model

### 4.1 `telemetry.readings`

Complete MQTT telemetry snapshots.

- `id`: identity
- `message_id`: source record identity
- `replay_session_id`: session identity
- `replay_cycle_id`: replay cycle identity
- `replay_cycle_number`: logical cycle number
- `line_id`: process line
- `event_ts`: original source event timestamp
- `received_at`: server receipt timestamp
- `payload`: full JSON telemetry object

### 4.2 `telemetry.events`

Operational and alarm events.

- `id`, `line_id`, `event_type`, `event_code`, `severity`, `state`
- `title`, `description`, `event_ts`, `recorded_at`
- `reading_id`, `replay_cycle_id`, `details`

### 4.3 `telemetry.alarm_state`

Current alarm rule state per line, rule key, and active event code.

## 5. Data flow

1. MQTT payload arrives on `factory/line30/telemetry`.
2. Subscriber decodes and validates JSON.
3. Persistence writes the reading and alarm events.
4. Successful writes acknowledge MQTT and broadcast live events to subscribed
   frontends.
5. The dashboard receives live updates on Socket.IO and merges them into the
   current line view.
6. Initial and historical data comes from REST endpoints.
7. CSV exports are generated by the API and downloaded through the UI.

## 6. API endpoints

| Method | Path | Description |
| --- | --- | --- |
| GET | `/api/health` | database and MQTT connectivity |
| GET | `/api/telemetry/latest` | newest reading for a line |
| GET | `/api/telemetry/history` | paginated telemetry history |
| GET | `/api/telemetry/statistics` | min/max/avg for a field |
| GET | `/api/summary/hourly` | hourly summary for a cycle or window |
| GET | `/api/events` | operational event history |
| GET | `/api/history/cycles` | replay-cycle completion classification |
| GET | `/api/exports/hourly-summary.csv` | CSV export of hourly summary |
| GET | `/api/exports/readings.csv` | CSV export of readings |
| GET | `/api/exports/events.csv` | CSV export of events |

## 7. WebSocket / Socket.IO usage

- Client connects to `VITE_SOCKET_URL` with `transports: ["websocket"]`.
- Client must emit `join_line` before receiving live data.
- Server routes live data to `line:{line_id}`.
- Channels are `telemetry_update` and `operational_event`.
- Reconnection is enabled with unlimited attempts and a 5-second maximum
  delay.

## 8. Frontend architecture

The UI is a single Vue 3 application.

- `App.vue`: root shell, global chrome, and view navigation.
- `telemetryStore.js`: Pinia store, source of truth for live and historical
  state.
- `api.js`: HTTP service.
- `socket.js`: Socket.IO client helper.
- `ProcessChart.vue`: ECharts wrapper for live trends and scatter charts.
- `HourlySummaryView.vue`: historical time-line, hour selection, and exports.

State groups:

- Live telemetry, latest reading, current cycle.
- Historical summary, selected hour, readings, events, cycles.
- Loading, error, export, connection, and refresh coordination.

## 9. Backend architecture

- `server/run.py`: entry point.
- `server/app.py`: application factory.
- `server/config.py`: environment validation.
- `server/api/`: REST routes.
- `server/sockets/`: Socket.IO join/leave and emit helpers.
- `server/repositories/`: SQLAlchemy queries.
- `server/services/`: business logic and response shaping.
- `server/database/`: engine and connection helpers.
- `server/mqtt/`: subscriber and message handler.

## 10. Deployment requirements

- PostgreSQL 12+ with the schema from `db/schema.sql`.
- MQTT broker reachable on `MQTT_HOST:MQTT_PORT`.
- Socket.IO CORS allowlisted origins, default:
  `http://localhost:5173,http://127.0.0.1:5173`.

## 11. Configuration reference

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | required | PostgreSQL connection string |
| `DB_POOL_SIZE` | `5` | SQLAlchemy pool size |
| `DB_MAX_OVERFLOW` | `2` | connection pool overflow |
| `DB_POOL_TIMEOUT` | `30` | pool timeout |
| `MQTT_HOST` | `127.0.0.1` | MQTT broker host |
| `MQTT_PORT` | `1883` | MQTT broker port |
| `MQTT_KEEPALIVE` | `60` | MQTT keepalive |
| `MQTT_TOPIC` | `factory/line30/telemetry` | MQTT telemetry topic |
| `MQTT_QOS` | `1` | MQTT QoS |
| `MQTT_CLIENT_ID` | `line30-flask-subscriber` | MQTT client id |
| `SOCKETIO_CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | Socket.IO CORS origins |

## 12. Testing and verification

The backend is a Python Flask package and is verified with `python -m py_compile`
and `ast.parse` on the source files.

The frontend is a Vue 3 + Vite package and is verified with `npm run build`.

Manual verification should follow:

1. Start PostgreSQL and apply `db/schema.sql`.
2. Start the MQTT subscriber and broker.
3. Start the Flask server.
4. Start the Vite frontend.
5. Observe `SOCKET CONNECTED` and live telemetry in the browser.
6. Switch to the history view and verify cycle selection, hourly rows, and
   exports.

## 13. Known limitations

- The dashboard expects MQTT QoS 1 with a configured broker.
- Live processing assumes `line_id` is `line30`.
- Historical CSV exports are scoped to the selected cycle and hour.
- The implementation does not include unit or integration automation for
  this integration snapshot.
